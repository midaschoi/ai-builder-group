**제안** — TR-01 인수 조건에 시점을 명시한다:

> 우리 계정 생성 금지 → **최종 인계 시점 기준.** 개발·경쟁 단계의 빌더 개인 속성은 허용하되,
> 인계 시 클라이언트 계정으로 이전하고 개인 속성은 삭제한다 (NFR-17 이관 체크리스트에 항목 추가).

⛔ 정정하지 않으면 검수 때 **G6(전환 측정 성립) 판정이 사람에 따라 갈린다.** 승인 필요.

```sql
  using (auth_user_id = auth.uid()) with check (auth_user_id = auth.uid());
```

RLS 는 컬럼을 가리지 못하므로 **빌더가 자기 행의 `role` 을 `admin` 으로 바꿀 수 있다.**
원래 주석은 "역할·활성 상태는 서버 액션에서 별도로 막는다"였지만, PostgREST 엔드포인트는
공개 주소이고 publishable key 는 공개용이라 **우리 화면을 거치지 않고 직접 요청하면 그대로 통과**한다.
PRD §2.2 "관리자 승격은 DB 직접 변경으로만" 이 화면에서만 지켜지고 있었다는 뜻이다.

**조치** — `supabase/migrations/0004_builders_column_guard.sql` 을 SQL 편집기에서 실행한다.
`authenticated` 롤의 UPDATE 를 회수하고 프로필 컬럼(`name` `slug` `one_liner` `role_label` `avatar_url`)에만 다시 준다.
`role` 은 어느 롤에도 주지 않는다.

> 적용하지 않아도 화면은 그대로 동작한다. **막히는 것은 우회 경로뿐이다.** 그래서 더 잊기 쉽다.

### 1.7 공개 웹 DB 연결 — ✅ 완료 (2026-08-17) · 확인 2건

§1.1-2 와 §1.6 을 함께 처리했다.

| 항목 | 결과 |
|---|---|
| `/work/[slug]` · `/insight/[slug]` 동적 라우트 | ✅ 발행분 SSG + 이후 발행분은 요청 시 생성 |
| `/insight/[category]` | ✅ `[slug]` 한 라우트에서 카테고리 → 글 → 301 순으로 해석 |
| 목록 DB 연결 | ✅ 발행분이 0건이면 시연용 샘플로 화면 유지 |
| 301 리다이렉트 서빙 | ✅ 상세가 못 찾았을 때만 `redirects` 조회 — 정상 경로 비용 0 |
| `llms.txt` (SR-03) | ✅ 발행 콘텐츠 포함 |
| JSON-LD 3종 (SR-04) | ✅ Organization(전역) · Article · BreadcrumbList(상세) |
| sitemap | ✅ 발행 슬러그·카테고리 포함, 시안 고정 2장 제외 |

**확인 1 — 301 이 아니라 308 이 나간다.**
Next 의 `permanentRedirect` 는 308 을 쓴다. 301 은 브라우저가 POST 를 GET 으로 바꾸는
문제가 있어 308 이 그 자리를 대신하고, **검색엔진은 둘을 같게 취급한다.**
정확히 301 을 내보내려면 미들웨어로 옮겨야 하는데 그러면 모든 요청이 DB 를 한 번 더 친다.
→ **SR-06 · DR-08 의 "301" 문구를 "301 또는 308(영구 이동)" 으로 정정 제안.**

**확인 2 — 시연용 샘플이 아직 살아 있다.**
`work/view.tsx` 의 `PROJECTS`, `insight/view.tsx` 의 `ARTICLES` 는 **발행분이 0건일 때만**
쓰인다. 하나라도 발행되면 목록 전체가 DB 로 바뀐다.
→ 오픈 전에 두 배열과 대응 이미지를 지운다 (README §절대 규칙 · 미동의 샘플).
→ `/work-detail` · `/insight-detail` 시안 2장도 그때 함께 정리한다. 지금은 sitemap 에서만 뺐다.
